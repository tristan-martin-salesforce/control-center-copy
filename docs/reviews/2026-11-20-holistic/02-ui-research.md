# UI-RESEARCH review: what a great UI looks like for Control Center (outward-looking half of ask #1)

Reviewer: UI-RESEARCH. Method: code and docs read (UX.md, UI-SPEC.md, DESIGN-V2.md, TENETS.md, `src/components/{home,shell,lists,today,chat}`, `src/engines/home/build.ts`, `app/outbox/_outbox`), plus web research (URLs inline). I did not run the app or take screenshots, so every statement about "what the user sees" comes from code and docs, not pixels. A sibling UI-AUDIT reviewer owns the inward critique; a PACKAGING reviewer owns the technical packaging decision.

## 1. Summary

1. The app's *specs* are already close to best-in-class (top-3 first, stable order, "N new" pill, undo over confirm, why-lines, Outbox with `a`/`e`/`j`/`k`). The gap is not missing principles; it is that **the product has too many nouns and too many places where the same decision is asked** (Home, Outbox, Triage, Activity > Needs you, Work, Assistant cards all hold "things awaiting you"). Best-in-class products converge on **one queue per kind of decision, drained in one keyboard flow** (Superhuman's Done, Linear Triage's accept/decline/duplicate/snooze, HubSpot task queues).
2. The single most transferable idea for the owner's goal ("never lose track; almost no time on admin"): **a drain-the-queue mode** ("Review mode"): full-screen, one card at a time, keys `a`/`e`/`s`/`x`, progress "3 of 11", ends on a "That's everything" screen. Home becomes a briefing that *launches* these modes, not a place that hosts a list of drafts. Today Home's "Approve N" is just a link to `/outbox` (`src/engines/home/build.ts:1422`).
3. For "log my week / log this meeting": the pattern across Gong, Salesforce activity capture, Fireflies, Demodesk, Affinity is **propose with a confidence, show the top candidate pre-selected plus 2-3 alternatives, never silently write**. Notably, these tools themselves mis-attribute when several opportunities exist (Gong picks one and puts the others in a custom field; EAC attributes mostly to account). That validates the owner's "give me a rundown of the opportunities so I can add quickly" ask and the app's approval-gated stance (*tenet: Nothing leaves without approval*).
4. AI-approval UIs have converged on: **plan first, editable; per-change accept/undo; bulk accept; checkpoints; and a trend toward fewer prompts** (Claude Code reports users approve 97% of permission prompts, which is why it added classifier-based auto mode). Lesson: approval fatigue is the failure mode. Batch by *policy and confidence*, make the unusual item loud and the routine item one keystroke.
5. A localhost browser tab loses: always-on presence, reliable OS notifications when no browser window is open, a dock/menubar badge, a global hotkey for quick capture, and launch-at-login. These are exactly what the "calm notifications" principle and the 8:30am-brief idea need. (One section, section 6; decision belongs to PACKAGING.)

**Home** (`src/components/home/HomePage.tsx:1-26`): masthead sentence, day ribbon, Do now (3 cards plus capacity), "Looks done: confirm", then verb columns, capped at 3 rows (5 at >=2400px) (`src/engines/home/build.ts:70`), "See all N", closing line "That's everything for today". Rows: title, one why line, quiet verb, filled button only on the selected row (`Sections.tsx:15-60`; `DESIGN-V2.md:25`). Click/Enter opens a right panel (Details | Assistant).

**Live behaviour** (`docs/UX.md:15-33`): push not poll, stable order, arrivals tinted, "N new - Show" pill, departures fade, selection survives, no toasts for background events. This is genuinely excellent and matches the best practice below; keep it.

**Notifications**: an in-page OS `Notification` is fired only when the tab is hidden and permission is granted (`src/client/providers.tsx:44-46`). Nothing exists when the browser is closed.

## 3. Research: what others do (extracted patterns, with sources)

### 3a. Daily planning and task cockpits
- **Sunsama: ritualised bookends.** A guided morning planning flow (pick tasks, estimate, schedule into blocks, about 10-15 min) and a *shutdown* that reviews what was done, carries unfinished items forward and tells you to stop; an in-app notification opens the shutdown at a time you chose in the morning; evening planning can merge both into one flow ([features](https://www.sunsama.com/features/daily-planning-and-shutdown), [changelog](https://roadmap.sunsama.com/changelog/daily-shutdown), [help](https://help.sunsama.com/docs/evening-daily-planning)). Transferable: the day has a start and an *end state*; unfinished work is explicitly carried (not silently piling up). Control Center already has "A day that ends" (`DESIGN-V2.md:36`) but no shutdown ritual that sweeps leftover items and the unlogged hours.
- **Things 3: two-part Today.** Today holds daytime items; "This Evening" is a separate section at the bottom; Upcoming merges scheduled to-dos, deadlines and calendar events grouped by week/month as it gets further out ([Things on App Store story](https://apps.apple.com/us/story/id1437936658), [MacStories review](https://www.macstories.net/?p=48965)). Transferable: Home's "Think ahead" strip already does the 14-day idea; the "this evening" split suggests a "later today / after hours" bucket that does not count against 8:30am capacity.
- **Motion / Reclaim / Akiflow: auto-schedule spectrum.** Akiflow is manual time-blocking from one inbox; Reclaim schedules tasks into calendar gaps by priority and due date and yields habits to important meetings; Motion is the most aggressive full auto-scheduling ([Reclaim comparison](https://reclaim.ai/blog/motion-vs-reclaim), [Akiflow comparison](https://akiflow.com/blog/akiflow-vs-reclaim), [Asian Efficiency](https://www.asianefficiency.com/schedule-management/motion-vs-reclaim/)). All vendor-authored; I found nothing independent on how often users override auto-moves (unverified). Transferable: stay on the *Akiflow end* for commitments (user places), use the *Reclaim end* only for "suggested" blocks. DESIGN-V2's rule "count only hands-on, today-scoped time; say overbooked only when true" (`DESIGN-V2.md:51-61`) is the right correction for over-aggressive schedulers.
- **Amie**: inbox of unscheduled to-dos next to the calendar; drag a to-do to a slot; AI proposes slots ([docs](https://amie.so/documentation/features/tasks)). Transferable: the day-spine already does this; do not copy the product (it reportedly pivoted toward notes, [review](https://www.usecarly.com/blog/what-happened-to-amie/)).
- Not researched in depth: Morgen (search returned nothing usable).

### 3b. Communication triage
- **Superhuman:** Cmd+K shows the action *and its single-letter shortcut* so the palette teaches the keyboard; split inboxes by sender/domain/label; single-key reply, Cmd+Enter to send ([Shortcuts and Cmd+K](https://help.superhuman.com/article/478-superhuman-command), [Split Inbox](https://help.superhuman.com/article/581-split-inbox-basics), [shortcuts](https://help.superhuman.com/hc/en-us/articles/45191759067411-Speed-Up-With-Shortcuts)). "Write with AI" drafts from a short prompt in your voice. Transferable: ⌘K already exists here; make every row-level verb show its key inline in the palette (verify: not checked in code). The "done = archived, inbox zero" semantic is the emotional payoff the app lacks: items "Done" here are not visibly counted down.
- **Linear Triage:** a distinct inbox for incoming work with four verbs: Accept (to default status), Decline (cancel, with comment), Duplicate (pick canonical, attachments move), Snooze (reappears when time passes; new activity cancels the snooze) ([triage docs](https://linear.app/docs/triage), [snooze](https://linear.app/docs/snooze), [routing guide](https://linear.app/enablement/guide/routing)). Triage Intelligence can suggest properties ([docs](https://linear.app/docs/triage-intelligence)). Linear Inbox now has a Priority tab separating "needs attention" from other updates ([changelog 2026-09-03](https://linear.app/changelog/2026-09-03-priority-inbox)) and caps open notifications (2,000) with auto-archive ([notifications](https://linear.app/docs/notifications)). Transferable: Control Center's Triage already has accept/dismiss/snooze; add **Duplicate/merge into existing item** as a first-class verb, and **auto-archive with a visible cap** to keep it from becoming the firehose.
- **HEY:** The Screener holds first-time senders until you say yes/no once; accepted senders route to Imbox, Feed (read-when-you-want) or Paper Trail (receipts); routing is per sender, overridable per message ([how it works](https://hey.com/how-it-works), [Screener](https://help.hey.com/article/722-the-screener), [Imbox](https://help.hey.com/article/759-imbox)). Transferable: **decide once per source, apply forever** is exactly "one-click corrections become rules" (*tenet: Suggest, then learn*); the missing piece is a visible "Screener" moment: first time a Slack channel/sender/recurring meeting appears, ask once.
- **Shortwave:** bundles group like items for batch handling; splits by query ([Shortwave](https://shortwave.com/), [Zapier comparison](https://zapier.com/es/blog/shortwave-vs-superhuman)). Transferable: bundle by *decision type* (e.g., "7 meeting-notes follow-ups from Globex") instead of by source.
- **Slack:** Later was renamed To-dos (items with reminders) and Saved; a unified Activity feed with bulk-clear and planned AI ranking; Catch Up as swipe-through unreads ([help](https://slack.com/help/articles/55757634348435-Later-is-now-To-dos), [Activity](https://slack.com/intl/es-hn/blog/news/slack-activity-triage-for-notifications), [TechRadar](https://techradar.com/pro/slacks-new-feature-wants-you-to-swipe-right-on-all-those-unread-alerts)). Transferable: card-by-card "catch up" is the same drain-mode idea.
- Not researched: Height (shut down; no usable results), Linear's own design-principles page (the "Linear Method" results were about issue practices; [Figma interview](https://www.figma.com/blog/the-linear-method-opinionated-software/) supports "opinionated defaults at the atomic level").

### 3c. Sales productivity and CRM activity capture
- **Gong:** exports calls/meetings to Salesforce as tasks/events; matches mainly on participant email, adjustable with rules (phone, calendar association, domain); when linked to several opportunities it selects one and lists the others in a custom field (`Gong_Associated_Opportunities__c`) ([Gong help](https://help.gong.io/v1/docs/configure-salesforce-tasks-or-events), [associating accounts](https://help.gong.io/hc/en-us/articles/360061370332-Associating-Salesforce-accounts-and-leads-to-calls)). Transferable: **primary opp plus "also touches" list** is the right data shape for the owner's "possibly several opps per time entry".
- **Einstein Activity Capture / Momentum (third-party claims only):** a competitor reports EAC resolves to the opportunity via contact roles and often attributes to the account instead, and one calendar event per attendee; Momentum picks the open opp with most contact roles among attendees ([Weflow](https://www.weflow.ai/blog/eac-mismaps-multiple-opportunities), [Weflow on Momentum](https://www.weflow.ai/blog/can-momentum-replace-gong-or-clari-copilot)). Vendor bias: verify against Salesforce docs. Transferable heuristic for the matcher: *external attendee emails -> contacts -> open opps with most contact-role overlap*, then rank.
- **Fireflies, Demodesk, Affinity, Granola:** all route CRM writes through a review step: field-level preview, accept/edit/reject, nothing sent until you click ([Fireflies](https://guide.fireflies.ai/articles/1729159683-autofill-crm-for-salesforce-automatically-extract-and-sync-meeting-data-to-contacts-accounts-and-opportunities), [Demodesk](https://demodesk.com/blog/how-to-configure-ai-crm-concierge-to-auto-sync-meeting-data-to-sale), [Affinity](https://support.affinity.co/s/article/Getting-your-meeting-notes-into-Affinity), [Granola->Salesforce](https://www.granola.ai/blog/meeting-notes-to-crm-automation)). Granola suggests contact records from attendees on Share. Transferable: field-level proposals with accept/edit/reject per field, one "Apply all" for the confident ones.
- **HubSpot task queues:** queues are labels that group, filter and share tasks; you work them back to back; up to 20 queues per user; workflows can feed a queue ([HubSpot](https://knowledge.hubspot.com/tasks/use-task-queues?t=28366)). Transferable: a queue is a *mode of working a filtered list*, not a new page.
- Not found in search: Scratchpad, Dock, Attention, Clari specifics. I did not fetch their sites; no claims made.

### 3d. AI approval queues and "proposed changes you apply"
- **Cursor:** floating review bar at the bottom: accept/reject for current file, next file with pending changes; line-level reject then Accept all; each change has Keep/Undo, each file Keep File/Undo File; pending changes persist across follow-ups ([Cursor docs](https://docs.cursor.com/agent/review)). Forum threads show users angry when per-change review disappeared or "Undo all" was destructive ([forum](https://forum.cursor.com/t/per-change-keep-undo-buttons-missing-after-agent-edits-only-undo-all-available/158983), [forum](https://forum.cursor.com/t/agent-review-undo-all-reverts-working-tree-on-disk-destructive-not-dismiss-only/164690); user reports, anecdotal). Lesson: per-item control plus bulk, and bulk undo must be scoped and non-destructive.
- **Claude Code:** plan mode blocks edits until you approve a plan; approval offers "start in auto mode / accept edits / review each edit"; Anthropic says users approve 97% of permission prompts, motivating classifier-based auto mode ([permission modes](https://code.claude.com/docs/en/permission-modes), [auto mode](https://anthropic.com/engineering/claude-code-auto-mode)). Lesson: **one plan gate up front, then trust level chosen at the gate**, because per-action prompting teaches rubber-stamping (a risk to *tenet: Trustworthy*).
- **Devin:** proposes a plan and waits only when low-confidence; otherwise proceeds with a 30-second feedback window; asks clarifying questions to raise confidence ([Devin 2.1](https://cognition.ai/blog/devin-2-1), [interactive planning](https://docs.devin.ai/work-with-devin/interactive-planning.md)). Lesson: *confidence-gated interruption* maps onto the app's Sure/Likely/Guess (`UI-SPEC.md:25`).
- **Lindy:** per-action "Ask for Confirmation" toggle, optionally conditional ("if outside scope") ([docs](https://docs.lindy.ai/testing/human-in-the-loop)). **Relay.app** had a human-in-the-loop approval step but is reportedly shut down (sources conflict on date) ([Relay](https://relay.app/features/human-in-the-loop); status via [Carly](https://www.usecarly.com/blog/human-in-the-loop-automation-tools/)), so cite as precedent only.
- **Copilot Workspace:** task -> editable specification -> editable plan (add/remove/edit per-file steps) -> implementation; editing an upstream stage regenerates downstream ([githubnext manual](https://github.com/githubnext/copilot-workspace-user-manual/blob/main/overview.md), [GitHub blog](https://github.blog/news-insights/product-news/github-copilot-workspace/)). Product status uncertain (conflicting source). Lesson: show the *plan* as editable data before the *artifact*; for the Assistant's multi-step proposals and for backfill ("log my week").
- Not found: cost display conventions in these products. I did not verify how any shows spend/progress; the owner's ask #5 (estimate up front, raise a hand during) is therefore from first principles, not precedent.

### 3e. Review-queue conventions and "calm software"
- Superhuman and Linear establish the convention set: j/k move, a single key per verb, Cmd+K lists verbs with their keys, snooze with natural-language times, undo toast after every irreversible-ish step ([Superhuman](https://help.superhuman.com/article/478-superhuman-command), [Linear snooze](https://linear.app/docs/snooze)). I could not find a single authoritative source for the "N new pill" convention; it is common in feeds, and the app's own implementation (`docs/UX.md:21-24`) is the reference.
- **Basecamp Calm:** a published list of principles (protect attention, async first, meetings last resort) ([Basecamp Calm](https://public.3.basecamp.com/p/RSArnoBAtaePG2TPTN7WGcAd)); Basecamp 3 "Work Can Wait" silences notifications outside your set work hours (default 8am-6pm) ([post](https://signalvnoise.com/svn3/basecamp-3-work-can-wait)); Basecamp's automatic check-in asks "What did you work on today?" at 16:30 ([guide](https://basecamp.com/guides/how-we-communicate)). Transferable: **work-hours-aware notifications** and a **daily "what did you work on" prompt**: that is the seed of the time-logging flow (log as you go, not on Friday).
- **Ambient UI:** the one source found says use changes in UI ambience for non-urgent info and ask only for minimum attention ([MEX](https://www.mobileuserexperience.com/design-principles-for-ambient-ui/4881/)). I found **nothing** by Julian Lehr or Rauno Freiberg, so cannot cite them (unverified; do not quote them in docs).
- Linear Inbox: separating a Priority tab from the rest and capping/auto-archiving ([changelog](https://linear.app/changelog/2026-09-03-priority-inbox)) is a direct template for "one more channel of noise" risk.

## 4. Findings

**UIR-1 (major): Too many "waiting on you" surfaces; the same decision lives in 5 places.** Drafts: Home "Reply & approve", Outbox, an Assistant card, Work item panel, and Triage. Logging approvals: Activity > Log it, Activity > Needs you, Home "Log & fix". Evidence: nav (`nav.ts:42-63`), Home sections (`build.ts:1422-1423`), Outbox sections (`OutboxPage.tsx:1-12`), Activity tabs (`UX.md:44`). Best-in-class has one inbox per decision type and a single drain flow. This is the structural cause of "drafts on Home as a long list" feel: Home shows 3 rows but "Approve N" just navigates away (`build.ts:1422`).

**UIR-2 (major): No "drain" mode.** Outbox has `a`/`e`/`j`/`k` on a list plus a side panel, but no one-card-at-a-time review with a progress count and a terminal "all clear". Superhuman, Slack Catch Up, Linear Triage and HubSpot queues all do. Evidence: `OutboxPage.tsx:12` (list + details), no queue/focus component found under `src/components/lists` (grep-level only; not exhaustively verified).

**UIR-3 (major): Naming load.** Home, Today, Work, Triage, Deals, Briefs, Agents, Activity, History, Outbox, Assistant, plus inside Activity six tabs, plus internal terms (canvas, landing, Stage/Apply, Slackbot hand-off). A new teammate cannot predict where a thing lives (owner ask #1 "easy for others to pick up"). `UX.md` itself is ~100 very dense lines on Activity alone (`UX.md:44-47`). Linear's lesson: few objects, many verbs ([Figma interview](https://www.figma.com/blog/the-linear-method-opinionated-software/)).

**UIR-4 (major): Time logging is a ledger UI, not a capture flow.** Activity is organised around the *record system's* states (Ready to log, Needs you, Weeks, Ledger, Use cases, landings Org62/VDP; `UX.md:44-47`, `UX.md:93-101`). Competitors organise around the *meeting*: the meeting arrives, the system proposes opp(s), you confirm in one action (Gong, Fireflies, Demodesk, Granola above). The owner's "I don't want to think about this" requires the former to be hidden behind the latter.

**UIR-5 (minor): Confidence is categorical in spec but not obviously the *driver of interruption*.** `UI-SPEC.md:25` defines Sure/Likely/Guess; Devin shows the interruption policy should be driven by it (only Guess and unresolved items interrupt; Sure ones batch-apply with an auto-closed list, as *tenet: Suggest, then learn* already allows for closes).

**UIR-6 (minor): Presence gap.** Notification path requires a hidden tab with permission (`providers.tsx:44-46`); no quick capture outside the tab (UI-SPEC section 13 specifies capture, but only in-page). Section 6.

**UIR-7 (minor): No shutdown/closeout ritual.** "That's everything" exists on Home (`DESIGN-V2.md:36`), but nothing sweeps leftovers, unlogged hours and tomorrow's carry-over (Sunsama shutdown; Basecamp 16:30 check-in).

**UIR-8 (minor): Spend/plan UX for the Assistant is unresearched.** No precedent found for up-front cost estimate plus mid-run "raise a hand"; recommend designing it as Devin-style *plan with estimate* gate (Section 5 P9). Relates to owner ask #5; coordinate with the COST/ASSISTANT lanes.

### 6b. "Approve drafts" flow

1. Press `R` (or click "Drafts to approve 4") anywhere. A focus view opens: left, the destination preview in its real format (Slack message in thread context, Gmail with quoted thread); right, a compact card: *why drafted*, evidence chips, confidence, "will post to #globex as you", dry-run/live state.
2. Keys: `a` approve (starts the undo window and shows "Sending in 10s - Undo" as a bottom toast, then auto-advances), `e` edit inline (typed text is protected from live updates, as today), `s` snooze (natural-language), `x` reject with optional reason (reason becomes a learning signal, *tenet: Suggest, then learn*), `j/k` skip/back, `o` open source, `?` why.
3. Header shows "2 of 4 - ~1 min left" and a segmented bar. A "Approve all sure (3)" button appears only if items are Sure and share a destination type; it opens one confirm that lists them (preserves *tenet: Nothing leaves without approval*; one click per batch rather than per item, a policy question, see Decision D2).
4. End screen: "All clear. 4 approved (undo), 0 failed. Next scan in 12m." Failures stay as a Retry card, not a toast.

Compared to today: Outbox is a sectioned list with a side panel and per-draft confirm in "Approve all" (`OutboxPage.tsx:4-6`). Justified parts: approve-then-confirm-then-undo-window is mandated by *tenet: Nothing leaves without approval*; keep. Unjustified: the list/panel layout, which is a surface choice, not a tenet.

### 6c. "Log my week" flow (daily trickle plus Friday sweep)

Principle: the week is logged by the *meeting stream*, not at the end; Friday is a 60-second sweep.
1. **Trickle.** After each customer meeting ends, a quiet prompt (badge, or notification if packaged) offers "Globex discovery, 1h: Globex - Platform Pilot (92%). [Confirm] [Other...]". One key. Internal work gets the internal type silently (as `UX.md:56-57` already specifies).
2. **Rundown when unsure.** If top match <~70% or two opps tie: card lists up to 4 opps with reason lines ("Dana + 2 attendees are contact roles on A; hours on B this week; #globex channel maps to B"), plus "Internal", "Add a second opp". Choosing one teaches the rule (P6).
3. **Friday sweep (or closeout).** One review mode "Confirm hours": rows grouped by day, each with a pre-selected opp and hours; Sure rows ticked, Likely rows pre-selected unticked, Guess rows opened as rundown. Header shows the quarter pace (as today). `a` approves a row, `A` approves the ticked group (one confirm). Out of this come canvas items (D-47) and DC suggestions ("claim DC on Acme? you logged 4h this month") as follow-up cards in the *same* flow, not a different tab.
4. **Result.** "Week logged: 31h, 28 in Org62 once Applied. Apply canvas? [Stage/Apply]." The landing states (staged/sent/in Org62/differs) stay visible *after* the flow in Ledger, but are not part of the decision path.

What differs from today: today's ledger-first Activity tabs expose the system's states (landings, writes) as the navigation (`UX.md:44-47`, `93-101`). That depth is justified by *tenet: Provenance on everything* and *Audit everything outbound*, but it belongs one level below the decision flow, not in it.

## 8. Packaging UX precedents (one section; PACKAGING owns the decision)

What the precedents show:
- **Raycast** is a resident menubar/launcher app: a global hotkey (default Option+Space) opens it from anywhere; commands can run on a schedule in the background, including menu-bar commands with a title/icon/menu; background refresh is off until the user enables it ([hotkey/settings](https://manual.raycast.com/settings), [background refresh](https://developers.raycast.com/information/lifecycle/background-refresh), [menu bar API](https://www.raycast.com/blog/making-our-api-more-powerful) cited via search snippet).
- **Granola** lives in the menu bar, detects a meeting from calendar events with 2+ attendees and from microphone use, and uses *its own pop-up windows* rather than macOS notifications (so it controls the "Take Notes" button) ([Granola notifications](https://docs.granola.ai/help-center/taking-notes/notifications), [review](https://www.bluedothq.com/blog/granola-review)). A one-minute-before-meeting reminder is documented there (a third party says five; versions differ).
- **Linear, Superhuman desktop**: I found no usable sources on their desktop packaging in this session (not verified); treat as unresearched.

What a localhost tab loses (web-platform facts, from MDN/Chrome docs; localhost-specific behaviour not verified):
- **Notifications when nothing is open.** A service worker can be restarted by the browser to handle push, but a Chromium dev thread reports that closing the last window of an installed web app may quit the browser and stop push on desktop ([Chromium thread](https://groups.google.com/a/chromium.org/g/chromium-dev/c/jqrtJCPMb-k), user report), and periodic background sync needs an installed app and an engagement score; it is unavailable in a plain tab ([Chrome docs](https://developer.chrome.com/docs/capabilities/periodic-background-sync)). Web push also needs a push service/VAPID setup (not verified for localhost).
- **Badge.** The Badging API works for installed apps on macOS/Windows, not in a plain tab ([Chrome docs](https://developer.chrome.com/docs/capabilities/web-apis/badging-api)). The existing OS notification in `providers.tsx:44-46` only fires while a tab exists and is hidden.
- **Global quick capture.** A web page cannot register a system-wide hotkey; capture (UI-SPEC section 13) only works with the tab focused.
- **Launch at login / resident presence.** The *worker* is already a LaunchAgent (README per CLAUDE.md, not re-verified); the *UI* is not resident, so "always-on presence" is not there.
- **Window identity.** A tab among 40 others; no dock icon, no Cmd+Tab. An installed PWA gets a window and dock icon and a badge (Edge docs: [notifications and badges](https://learn.microsoft.com/en-IE/microsoft-edge/progressive-web-apps-chromium/how-to/notifications-badges)).

Design implication (for PACKAGING): P8 (closeout), P12 (tiered notifications) and the 6c trickle prompt all depend on a resident surface; the cheapest step may be a menubar item plus a native notification from the existing worker, while the UI stays a localhost page. That is a design requirement from this lane, not a recommendation of a technology.

## 10. Decisions for Tristan

- **D1: How far to consolidate the nav (P13).** Options: (a) keep 11 destinations, fix Home only; (b) 5 primary + secondary drawer (recommended); (c) a single Home plus modes. Recommend (b); (c) costs discoverability for a tool with deep Deals/Work surfaces.
- **D2: Is a batch confirm acceptable as "approval"?** *Tenet: Nothing leaves without approval* says every outbound action goes through the Outbox and its approval gate; today "Approve all" is one confirm per draft (`OutboxPage.tsx:5`). A single confirm listing N drafts that the user can expand is weaker consent per item. This is a **blocker needing Tristan** if you want it; recommend allowing it only for drafts you have viewed in the focus mode (viewed-and-not-edited counts as reviewed), and never for first-time destinations.
- **D3: Time-logging default stance.** Options: (a) always confirm (today); (b) auto-stage Sure matches into the canvas but still require Apply (recommended: matches "don't make me think", keeps *Apply* as the gate); (c) auto-apply. (c) conflicts with the invariant that the app writes only on the user's Apply; not recommended.
