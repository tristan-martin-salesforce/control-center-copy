### P33-1 (M) A retention horizon past about 740,000 days fails the nightly run — `src/db/retention/policy.ts:50`, `src/contract/settings.ts:661-667`, `docs/reviews/2026-11-20-holistic/26-caps-audit.md:105`
**Fixed c9feb8d** (post-review33-fixes): `cutoff()` clamps at AD 1 (`CUTOFF_MIN_MS`, why in the comment); each rule runs under its own catch, the plan says `failed (<code>)` and an open Health event `DATA.RETENTION_RULE_FAILED` names the rule until its next clean run; `tests/db/retention/retention.pg.ts` runs the plan and the run at 740,001 days and at `RETENTION_DAYS_MAX` (both fail without the clamp) and a throwing rule. Audit row 105 of `26-caps-audit.md` not edited (outside this lane): it should say the bound is Postgres's AD 1.
The caps audit lifted the four horizons from 3,650 to `RETENTION_DAYS_MAX = 100,000,000` days and checked only that `now − days` stays a valid ECMAScript Date (it does: ±10⁸ days). It did not check Postgres. `cutoff()` returns `new Date(now − days·DAY).toISOString()`; any instant before AD 1 serialises as `-00xxxx-…` (or `0000-…`), and Postgres rejects both: `time zone displacement out of range: "-003449-01-28T12:00:00.000Z"`, `date/time field value out of range: "0000-06-01T00:00:00.000Z"`. The run's rule loop (`src/db/retention/run.ts`, `for (const rule of SQL_RULES)`) has no per-rule catch, so the first rule with that horizon throws and the data-retention job fails every night, for every table, including the ones with sane horizons. The Settings ▸ Data input has no max (`DataSection.tsx:91`), so a user who types a big number to mean "never" gets this. "Keep everything" (`retention.enabled`) is the off switch, but the contract advertises the big number as valid (`tests/contract/settings-bounds.test.ts` asserts it).
**Verify:** `node -e "const DAY=86400000, now=new Date('2026-11-21T12:00:00Z'); console.log(new Date(now - 2_000_000*DAY).toISOString())"` → `-003449-01-28T12:00:00.000Z`; `psql -d postgres -c "select '-003449-01-28T12:00:00.000Z'::timestamptz"` → error. Or in the app: Settings ▸ Data, one horizon = 5,000,000, "Run retention now" (dry) → the plan fails.
**Fix:** clamp in `cutoff()`: `const t = now.getTime() − days·DAY; return new Date(Math.max(t, AD1)).toISOString()` with `AD1` built by `setUTCFullYear(1, 0, 1)` on a zero date (`Date.UTC(1, …)` means 1901). A horizon that clamps deletes nothing, which is what the user meant. One test in `tests/db/retention/*` (or the contract bounds test) runs the plan at `RETENTION_DAYS_MAX` against the database. Update the audit row 105 to say the bound is Postgres's (AD 1), not ECMAScript's.

### P33-3 (L) A relay continuation counts a lookup that threw as done — `src/jobs/handlers/relay-guard.ts:106-112,118-125`, `src/jobs/handlers/org62-readback.ts:269-277`
**Fixed 023e7f6** (post-review33-fixes): the guard counts a lookup once `fn` returns and stops counting at the first throw on the leg, so the continuation starts at the failed batch (later batches of that leg are read once more; said in the guard's header). `tests/jobs/relay-guard.test.ts`.
`run()` does `lookups += 1` before `await fn()`, and `finish()` writes `relayDone = resumeAt + lookups`. The readback handler catches a batch's failure (`failCodes`) and goes on; when a later lookup passes the hold and asks, the continuation's `skipTo` includes the failed batch, so it is never read on that job; it waits for the next scheduled readback. Resume by position also re-reads a succeeded batch when a failure is not counted, so the count alone cannot be exact.
**Verify:** `tests/db/jobs/org62-readback*` with a `lookup` that throws on batch 2 and a governor that asks at batch 4; the continuation's `skippedBatches` is 4, batch 2 is not in the second leg.
**Fix:** carry what was read, not how many: `finish({ payload: { vars: { relayDone: <keys of batches that returned> } } })` and skip by key in readback; or, smaller, count in `finally` only when `fn` returned (`ok = true` after the await) and accept the one re-read. Say which in the handler's header either way.
