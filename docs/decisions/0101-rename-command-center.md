# D-101: Command Center everywhere: package, state folder, LaunchAgents and database renamed, with a boring folder migration

- **Status:** Accepted, built (2.0; chunk `p4-rename-command-center`) · builds [D-88](0088-ui-conventions-command-center.md)
- **Date:** 2026-11-21
- **Source:** [holistic review](../reviews/2026-11-20-holistic/README.md) H-10b; [wave 1/2 review](../reviews/2026-11-20-holistic/14-wave12-review.md) W12-11

## Context
D-88 settled the product name: **Command Center**, renamed everywhere including the package name and the state folder, with a folder migration on update. Until this chunk the UI said Command Center while the package, the state folder, the LaunchAgent labels (`com.controlcenter.*`) and the database (`control_center`) still said Control Center (W12-11). The state folder is also where the bundled Postgres cluster, its unix socket and the env file live ([D-98](0098-bundled-postgres.md)); the env file's `DATABASE_URL` percent-encodes the socket folder, and a 1.x Homebrew install has a TCP URL instead. Every 1.x install has to come across without losing data and without a manual step it can get wrong.

## Decision
- **Names.** Package `command-center`; state folder `~/Library/Application Support/command-center/` and logs `~/Library/Logs/command-center/` (one constant per language: `src/ops/paths.ts`, `scripts/ops/lib/paths.mjs`, and `src/db/client.ts` where infra cannot import `src/ops`; `tests/ops/pg-url.test.ts` keeps them in step); LaunchAgents `com.commandcenter.web|worker|db`; app database `command_center`; every UI string, page title, toast, palette entry, doctor/installer/updater line and script header says Command Center. Code identifiers stay: `CC_*` variables, `cc` prefixes, the `control_center_*` **test** database prefixes, the git branch and the repo folder (not user-facing). Port **4327 is unchanged**; `~/Projects/PORTS.md` is Tristan's manual edit, and doctor's registry check keys on the port, not the app's name.
- **The folder migration** (`scripts/ops/lib/migrate-state.mjs`, the only code that spells the old names; `tests/ops/rename-grep.test.ts` forbids them everywhere else). A state machine over injected deps, deciding from what is on disk: old folder only → migrate; both → use the new one, say so, never merge, never delete the old; only the new → nothing. Steps, one plain log line each: marker (travels with the folder) → stop the old agents (web, worker, then db) → `fs.renameSync` the folder (same volume) → the logs folder → rewrite the old state path in the env file, raw and percent-encoded → rewrite the cluster's own `command-center.conf` for the new socket path → write the new plists (the old ones with labels and folders replaced; the checkout they run is unchanged) → start the database agent → rename the database → start web and worker (every one whose new plist exists, not only the ones running when the move began: the 1.x updater's web restart spawns the move before the worker is bootstrapped, W34-1; an orphan old-label service exits when its env file is gone) → delete the old plists → mark `completedAt` in `migration.json` (`migratedFrom: 'control-center'`).
- **Idempotent and resumable.** The marker is written before the rename and says what was running, so a run that died anywhere after the rename is finished by the next one (`finish`); a run that failed before the rename changed nothing and restarts the agents it stopped. A lock file (pid) keeps two entry points from migrating at once. It never blocks a start: any problem is one plain line.
- **Database.** `ALTER DATABASE control_center RENAME TO command_center` through a `postgres`-database connection after ending the old database's sessions, only when `DATABASE_URL` is Command Center's own (the bundled socket, or the 1.x Homebrew default) and the URL's database is the old name. A TCP URL keeps its host and port and only its database name changes. A URL you set yourself is never touched. If the rename cannot happen (server down, both names exist) the old name stays, `DATABASE_URL` keeps pointing at it, one line says so, and every later setup/install/update/doctor run tries again (a service start does not). `ensureAppDatabase` renames a leftover `control_center` instead of creating an empty twin.
- **Entry points.** Every one runs the migration first: `setup`, `install` (and `install.sh` through it), `update`, `pg-cluster`, `ops:install/uninstall`, `backup`, `restore`, `rollback`, `doctor`, the `predev`/`predev:web`/`preworker` npm hooks, and the LaunchAgents' `run-service.mjs`. The last one is what makes one `npm run update` from a 1.x checkout enough: the 1.x updater (old code) fetches the new code, builds, backs up, migrates the schema and restarts the old-labelled services; those start `run-service.mjs` from the **new** checkout, see the old folder, and hand the move to a detached process (own session, so launchd's bootout of the old job does not reach it), which starts the new services. If `npm run doctor` still shows old names after two minutes, `npm run update` again finishes it.
- **Backups and restore.** `listBackups` under the default database name also lists `control_center-<stamp>.dump|.base.tgz`, ordered by timestamp, so `npm run restore` and `ops:rollback` accept backups made under the old name (a `pg_dump` restores into any name; a restored 1.x base backup that holds `control_center` is renamed by `ensureAppDatabase` at the next start). The folder moves with its `backups/`.
- **`scan:private`** reads names from the database under either name (`databaseUrlCandidates`), the resolved URL's first.

## Consequences
- A 1.x install changes folder, labels and database name once, on its first 2.0 start; nothing is lost and a failure at any point leaves a state the next run finishes from.
- The move writes the web and worker plists fresh from 2.0's template (loopback bind, D-76) rather than renaming the 1.x ones, and keeps the newest 1.x backup in `backups/pre-2.0/` out of retention (UPGRADING.md UPG-3, UPG-4).
- The old folder is never deleted: after "both folders exist" the user deletes it by hand (`docs/INSTALL.md`).
- A script or habit that greps `launchctl list` for `controlcenter` finds nothing after the move; docs and fixes say `commandcenter`.
- External, manual follow-ups (not code): `~/Projects/PORTS.md` row, the Slack channel's own name, the shared Drive folder's title; the announce text and release channel name in this repo already say Command Center.
